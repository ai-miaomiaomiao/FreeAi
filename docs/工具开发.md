# 工具开发

给智能体加一个「能动手」的能力，或者在改内置工具时不踩坑。插件接口（前端调用那套）见 [插件开发.md](插件开发.md)。

---

## 一、三套东西别混

| | 内置工具 | 插件工具 | 插件接口 |
| --- | --- | --- | --- |
| 调用方 | 模型（agent 循环） | 模型（agent 循环） | 前端 / 任何 HTTP 客户端 |
| 声明 | `TOOL_SCHEMAS` + `_HANDLERS` | `SCHEMA` + `run()` | `EXPOSE` + `fn(payload)` |
| 代码位置 | `src/agent_actions.py` | `src/plugins/<文件夹>/__init__.py` | 同左 |
| 描述来源 | `src/modeltips/tools.json` | 插件自己的 `SCHEMA` | 无（前端自己看） |
| 上下文 | 内核构造的 `ctx` | 同一个 `ctx` | 请求体 + 注入的 `ws` / `ai_dir` |
| 失败 | `ToolError` → `ok:false` | 抛异常 → `ok:false` | 抛异常 → HTTP 400 |
| 要不要改内核 | 要 | 不用 | 不用 |

「工具」只有前两列。改一个工具**永远先考虑写成插件**——插件不改内核，升级不吃力。

---

## 二、一个工具由什么构成

三件东西，缺一不可：

1. **schema** —— `TOOL_SCHEMAS` 列表里的一项：`{"type": "function", "function": {"name", "description", "parameters"}}`。
2. **executor** —— `_HANDLERS` 字典里 `名字 -> 函数`，函数签名 `(args: dict, ctx: dict) -> dict`。
3. **描述文案** —— 在 `src/modeltips/tools.json`，按工具名一条：`{"描述": {"description": "...", "params": {"参数名": "..."}}}`。

**代码里的 `description` 一律是空串**，运行期由 `model_tips.apply_tools()` 从 JSON 填进去。这是**严格模式**，出问题当场抛 `RuntimeError`，不静默退回旧文案：

- 表读不到 / JSON 写坏；
- 本次工具表里有的工具，在表里没条目、或 description 是空串；
- `params` 里写了代码里不存在的参数名（笔误）；
- 表里有、但本次工具表里没有这个工具名（多半是改名了没同步）。

改完 JSON **不用重启**：`model_tips` 按 mtime 热加载，下一轮请求就生效。改 `.py` 要重启服务。

> 插件工具的描述**不在** `tools.json` 里，也不参与上面的校验 —— 它们写在插件自己的 `SCHEMA` 里。

**参数全部必传。** 本项目的 schema 把每个参数都列进了 `required`，这次用不上的传空串 / `0` / `false`。漏传会直接报参数错误，比让执行器猜一个默认值可靠。

## 三、内置工具清单（22 个）

| 类别 | 工具 |
| --- | --- |
| 读 | `list_dir` `read_file` `find_files` `search_text` `locate_symbol` `diff_text` `image` |
| 写 | `write_file` `edit_file` `check_files` |
| 执行 | `run_command` `run_read`（只读命令通道） |
| 远端 | `remote_fetch` `remote_push`（SSH 与本机之间搬文件） |
| 外部 | `fetch_url` `web_search` |
| 交互 | `ask_user`（弹选项阻塞等人） `handoff`（派活给人工，不阻塞） |
| 会话 | `todo` `remind` |
| 流程 | `finish_stage`（多步流程交棒） |
| 管理 | `plugin_admin`（启停插件） |

`run_read` 与 `run_command` 是同一个底层、两条路：前者只能跑查看类命令、不许写盘，用来逼模型在排查阶段别乱改。

## 四、执行链

```
模型返回 tool_calls
  → agent_modes.filter_schemas(schemas, mode_id, stage_id)   按智能体 / 阶段裁表
  → agent_actions.execute(name, args, ctx)                   全链路唯一入口
      ├─ _HANDLERS 命中 → 内置 executor
      ├─ 否则 agent_plugins.has_tool → 插件 run_tool
      └─ 都没有 → {ok:false, "未知工具 …"}（列出可用工具名）
  → _norm_result     统一成 {ok, summary, content}
  → _clip_tool_content  按额度裁剪
  → 回灌 messages
```

三个要点：

**① `execute()` 是唯一兜底点。** 任何工具、任何插件抛出的任何异常（含 `SystemExit`）都只能变成这一次调用失败，不许穿透到 agent 循环：

- `ToolError` → `{ok:false}`，属"预期内的失败"（参数写错、路径越界），不刷日志；
- `KeyboardInterrupt` **原样抛出**——那是用户要停服务，吞掉就按不死了；
- 其余 `BaseException` → `{ok:false}` + 上报。

**② 内置优先，插件不能重名。** 模块末尾 `agent_plugins.register_builtin_tools(_HANDLERS.keys())` 把内置名单交给插件加载器，撞名时加载器报错而不是静默忽略（静默的话界面上两个都在，模型只拿到内置那个）。

**③ `filter_schemas` 有兜底。** 裁完一个工具都不剩就退回原表 —— 空工具表是这套系统最贵的故障：模型只能把调用写进正文，整轮静默失效。另外两类工具不受白名单约束（`ALWAYS_TOOLS`）：`finish_stage`（少了它流程卡在第一步）和 `handoff`（人工作业，不常驻等于模型看不见它）。没有流程的模式（如自由对话）会再把 `finish_stage` 摘掉 —— 留着它只会让模型空调一次。

## 五、ctx 里有什么

内核在每次请求时构造，所有工具共用这一个 dict：

| 键 | 含义 |
| --- | --- |
| `roots` | 可访问的根目录列表（`fs_roots` + 当前工作区），路径守卫用 |
| `cwd` | 进程基准目录（项目根），工作区为空时的兜底目标 |
| `workspace` | 本会话的工作区路径，**相对路径一律以它为基准** |
| `code_dir` | `src/`，插件目录所在 |
| `ai_dir` | 本工作区的 `.ai/`，会话数据、改动记录、放行清单都在里面 |
| `remote` | 远程工作区配置；非远程会话为 `None` |
| `session_id` | 会话 id |
| `cfg` | 本轮运行配置（模型、端点等） |
| `mode` | 本轮智能体 id，工具表按它裁剪 |
| `should_cancel` | 可调用对象，返回 `True` 表示用户要求停 |
| `emit` | 往 SSE 写事件；**只有 Web 对话窗口有**，微信 / 非流式接口没有 |
| `read_seg` | 本轮"哪个文件读过哪几行"的账本 |

**相对路径必须落在 `ctx["workspace"]` 上。** 传 `cwd` 或进程目录会串到别的项目里：典型症状是模型说读某文件，结果去找 `src/` 下同名的那份。

**带 `ssh://` 的路径会派生一个专用 ctx**（`agent_actions._ssh_path_ctx`）：`remote` 指向那个目标、`workspace` 是远端根、`roots` 为空，`ai_dir` / `session_id` / `should_cancel` 从原 ctx 透传。透传 `ai_dir` 不是可选项——不带的话远程写入不会记进 `.ai/edits/`，下一轮 system 的"上一轮改了什么"就漏。

## 六、并发、取消

**取消的检查点在「每个工具开跑前」，不在工具执行中。** 所以点了停止之后，正在跑的那个调用会跑完，下一轮才停。工具内部有长循环的，自己查 `ctx["should_cancel"]()`；`run_command` 更进一步，把 `should_cancel` 当 `stop_when` 传给底层，逐行轮转判断，另加独立 watchdog 做硬超时（不然命令一声不响卡住时永远轮不到判断）。

**`agent_llm.READ_ONLY_TOOLS` 里的工具并发执行**（线程池），目前 8 个：`list_dir`、`read_file`、`search_text`、`locate_symbol`、`find_files`、`diff_text`、`image`、`todo`。

两条约束：

- **只读≠不写 `ctx`。** `read_file` 往 `ctx["read_seg"]` 记账，写工具把对应文件的账作废——两边读写同一本账，所以记账要按线程安全的方式做。
- **`ask_user` 和 `handoff` 绝对不能进这张表。** 它们执行中途要往 SSE 里写事件，那条连接是同一个请求线程在用的；并发时两边同时写 `wfile`，事件会交错成半截 JSON。

## 七、返回值契约

```python
{"ok": True, "summary": "一句话（给人看的面包屑）",
 "content": "回灌给模型的正文", "data": {...给前端的数据...}}
```

- `content` 是模型看到的东西，写清"发生了什么、下一步可以怎么办"。
- `data` 只给前端，不进 messages。
- 返回 `None` **不算失败**：有工具只靠副作用（写盘、重启服务），会被归一成"完成（工具没有返回值）"。
- 例外：`image` 的图走结果里的 `image_url` 字段转多模态消息，`content` 只留一行尺寸/大小摘要——整份 base64 塞进 `content` 等于按文本 token 计价，一张截图几十万字符且每步全量重发。

**额度表**（`agent_llm.TOOL_RESULT_LIMITS`，实测值）：

| 工具 | 上限（字符） | 说明 |
| --- | --- | --- |
| `read_file` | 22000 | 工具层已按 20000 精确裁过并算好行号，这里留余量当保险 |
| `search_text` | 8000 | |
| `locate_symbol` | 8000 | |
| `list_dir` | 6000 | |
| `image` | 2000 | 内容只是一行摘要 |
| 其余（含插件） | 12000 | `DEFAULT_TOOL_RESULT_LIMIT` |

超限裁剪时**退到最近的换行处**，别切在半行上，并在尾巴明写"为什么裁、下一步怎么办"（翻页？加 glob？收窄 path？）。

## 八、模型侧兼容层

模型不总是老实按 schema 调，`src/agent_llm.py` 里有四层缓冲：

1. **`TOOL_ALIASES`** —— 工具名别名（`grep` / `rg` / `search` → `search_text`，`dir` → `list_dir`…）。
2. **`ARG_ALIASES`** —— 参数名别名（`command` / `shell` → `cmd`，`file_path` → `path`，`old` → `old_str`…）。只收"模型常写错的叫法"，不代表 schema 里的参数都登记过。
3. **`_canon_tool_name(raw, known)`** —— `known` 传本次请求工具表里真实存在的名字时放宽：别名映射不到但名字本身合法的也放行。这个必须放宽，否则不在别名表里的工具（插件、助理专属）哪怕名字写对了也会被丢掉，整轮作废。
4. **`_canon_args(tool, args)`** —— 三条规矩：别名表登记过的叫法换成我们的键；**没登记的键原样保留**；连别名表都没有的工具纯透传。另外把 XML 里的 `"true"` / `"false"` 还原成布尔（`<recursive>false</recursive>` 取到的是字符串，非空永远为真）。

`_PASSTHROUGH_ARGS` 是"明确要求原样保留"的声明，目前只有 `run_command` 的 `_confirmed` 和 `timeout`。

> 历史坑：以前 `_canon_args` **只保留别名表登记过的键**，没登记的工具参数被滤成空 `{}`，症状是"模型调了 svn，但 action 全是默认值"，日志上还显示调用成功。现在的规矩是"只改名、不删键"。

## 九、安全边界

**① 路径守卫 `agent_tools.core.resolve(path, roots, base)`** —— 所有文件类工具的第一行都过它，越界直接 `ToolError`。`base` 是相对路径的基准，**必须传会话 workspace**。带 `ssh://` 的路径走远程分支，不受本地 `fs_roots` 约束（边界变成那台机器上的目录）。

**② `run_command` 三档定级**（`agent_tools.core.classify_command`，只看命令串，不看上下文）：

| 档 | 含义 | 处理 |
| --- | --- | --- |
| `block` | 不可逆、一跑可能毁系统/数据（格式化、分区、关机重启、删根、改引导、提权） | **任何情况都不执行**，`_confirmed` 也救不回来 |
| `ask` | 可逆但可能删东西（`rm`/`del`/`rmdir`、`git reset --hard`、`git clean -fd`、强推、`svn revert`、`mv` 覆盖、`chmod -R`…） | 弹确认卡，人点头才跑 |
| `ok` | 其余全部 | 直接跑 |

分三档而不是一刀切，是因为大多数命令（`git status`、跑构建）本来就该直接跑；拦多了模型会改用更刁钻的写法绕过，反而更糟。

**字符串黑名单天生挡不住 `r""m -rf` 这类变形。真正的防线是审计日志 + ASK 档的人工确认**，黑名单只用来兜住最常见的误伤。每条命令（含用户自己在终端敲的）都写进 `agent.log`，带时间、完整命令、cwd、定级。

- `_BLOCK_PATTERNS` **不可配置**，界面上只读展示：改了等于把安全底线交出去。
- `_ASK_PATTERNS` 每条带一个**定级理由**字符串（如"rm 会删除文件"）。永久放行清单存的就是这个字符串，所以放行"rm 类"而不是"这一条命令"。
- `user_shell=True` 是用户自己在网页终端敲的命令：**不定级、不限目录**。理由：这是他自己的机器和终端。模型那条路上必须留着分级，因为模型会犯错。两条路共用同一个函数，靠这个参数分开。

**③ 确认卡五档**：允许一次 / 本轮自动放行 / 本会话自动放行 / 永久放行 / 拒绝执行。

- 等 **180 秒**（`CONFIRM_WAIT_SEC`），**有意比 `ask_user` 的缺省（600 秒）短**：确认卡是"命令已经算好、只等他点头"的封闭五档，等不到就按最保守一档走，代价小；`ask_user` 是真在问路，等不到只能瞎猜，所以要等满。别照抄成同一套数值。
- 永久放行落 `.ai/confirm_allow.json`（跟用户走、不进版本控制）；本会话放行是进程内内存，重启失效。
- `run_command` 的 `_confirmed` 参数**保留**：微信 / 非流式接口没有 `emit`，弹不出卡片，只能退回老路。但模型不再需要自己猜——以前是"拒绝 + 让模型带上 `_confirmed` 重试"，等于把确认按钮交给模型，用户桌面上什么都没弹，下一轮它自己就"确认"过了。

**④ `ask_user` 的单个选项不能是"确定 / 继续 / 执行"这类确认词**（会被拒），因为"只传 1 个选项"的语义是「阻塞版等人」，不是确认框。

## 十、新增一个工具

### 路线 A：写成插件（优先）

见 [插件开发.md](插件开发.md)。不用改内核、不用重启，`SCHEMA` 就是工具 schema，`run(args, ctx)` 就是 executor。

适合：某个具体软件/生态的能力（adb、gradle、svn、git）、有自己状态的、想做成可开关的。

### 路线 B：改内核加内置工具

只有「所有场景都要用、且必须和内核状态（`ctx`、会话、流程）深度耦合」时才走这条。

1. 在 `src/agent_actions.py` 写 executor：`def _t_xxx(args, ctx) -> dict`。
2. 在 `TOOL_SCHEMAS` 加 schema（`description` 留空串，参数全列进 `required`）。
3. 在 `_HANDLERS` 注册名字。
4. 在 `src/modeltips/tools.json` 补 `description` 和 `params`（**漏了会抛异常**，这是设计如此）。
5. 若它该被并发执行，加进 `agent_llm.READ_ONLY_TOOLS`；要往 SSE 写事件的**不许**加。
6. 若要限某些智能体/阶段可见，改 `src/modes/*.json` 的 `tools`。不写就默认对所有智能体可见（`finish_stage` 与 `handoff` 除外，见第四节）。
7. **重启服务**（`.py` 改动不会热加载），然后编译校验一遍。

### 检查清单

- [ ] 相对路径用了 `ctx["workspace"]` 作 base，没落回进程 cwd
- [ ] 文件类操作过了 `resolve()`
- [ ] 长循环里查了 `ctx["should_cancel"]()`
- [ ] 返回 dict 有 `ok` / `summary` / `content`，失败走 `ToolError` 而不是返回 `None`
- [ ] `content` 在最坏输入下不会爆额度；超了说明怎么翻页
- [ ] 描述写的是「做了什么、有什么客观后果」，不是「用户希望怎么用」（那是记忆的活）
- [ ] 插件路线：`run()` 自己吞异常，别指望内核兜（虽然 `execute()` 会兜，但会丢上下文）

## 十一、底层能力（`src/agent_tools/`）

内置工具的公共零件，写新工具时直接复用，别各写一套：

| 文件 | 内容 |
| --- | --- |
| `core.py` | 路径守卫 `resolve()`、文件读写（含编码判定与 BOM 处理）、目录列举、终端执行（`run_command` + 三档定级 + 审计）、记忆、日志 |
| `edits.py` | 改动记录落盘（`.ai/edits/`），驱动下一轮 system 的"上一轮改了什么" |
| `__init__.py` | 统一再导出，`agent_actions` 只 import 这一层 |

几个容易踩的约定：

- **编码判定只有一份**（`core._decode_enc`）：本地和远程必须共用，写回时按原编码编回。以前远程分支只试 utf-8/gbk 且不剥 BOM，同一文件两边行为不一致。
- **`read_file` 有 512KB 硬顶**，超了只读前半段并标 `truncated`；更大的文件用 `search_text` 定位或显式 `offset` 分段读。
- **`run_command` 的 `timeout` 是硬超时**，到点杀整个进程树。别在消费方自己循环里判超时——命令一声不响卡住时那个循环永远轮不到。

## 十二、调试与症状对照

入口：`GET /api/tools` 看当前工具表（含插件），`agent.log` 看每次调用与命令审计。

| 症状 | 原因 |
| --- | --- |
| 启动即 `RuntimeError: 工具描述表 …` | `tools.json` 写坏了：缺条目、`params` 里有代码里不存在的参数名、或表里有本次工具表没有的工具名 |
| 模型说"没有这个工具" | 工具被 `filter_schemas` 按智能体/阶段裁掉了；看 `modes/*.json` 的 `tools` |
| 工具"成功"但参数全是默认值 | 参数名没进 `ARG_ALIASES` 而被丢弃（老 bug）。现在"只改名不删键"，若还复现，检查是否是执行器自己 `args.get()` 的键写错了 |
| 工具返回"成功但没内容" | `content` 是空串；`_clip_tool_content` 会兜底认 `text` 字段，但两个都没有就只能给兜底文案 |
| 点了停止还在跑 | 检查点在"每个工具开跑前"，已开跑的那个会跑完；或工具内部没查 `should_cancel` |
| 一张图把成本拉爆 | 别把 base64 塞 `content`，走 `image_url` 多模态字段 |
| 插件工具和内置撞名 | 加载时报错，不会静默——看到报错就改名 |
| 改完 `.py` 没生效 | 工具是内核代码，要重启服务；只有 `modeltips/*.json` 和插件代码是热加载 |
